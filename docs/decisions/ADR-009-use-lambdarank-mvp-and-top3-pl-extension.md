# ADR-009: LambdaRankを予測MVPに採用しtop-3 Plackett–Luceへ拡張する

- Status: Accepted
- Date: 2026-10-06
- Decision Owners: Repository maintainers
- Supersedes: [ADR-004](ADR-004-select-market-adjusted-win-model.md)
- Superseded by: N/A

## Context

[要件定義](../requirements.md)はJRA平地重賞を評価対象とし、最終的には同じ判断時点の市場オッズより良い確率推定と、予算内での購入判断を目指す。[ADR-004](ADR-004-select-market-adjusted-win-model.md)は市場補正型の単勝確率を予測MVPに選んだが、モデルはまだ実装されていない。今回の要件変更では、まず上位馬の並び順を学習し、その後に同じ特徴量から着順確率を学ぶ段階構成を採用する。

データの発表・受信時刻の監査、同じ判断時点の市場基準との比較、レース単位の時間順検証は引き続き必要である。取得済みのオッズでも、過去の判断時点に利用可能だったことを確認できなければ、同時点の市場比較や購入評価には使えない。データ取得・加工・読み込みの境界はADR-007とADR-008を維持する。

## Decision

### MVP: LGBMRanker + lambdarank

予測MVPは、各レースの上位馬を正しく並べるランキングモデルとする。各馬の入力固定時刻までに利用可能だったことを確認した特徴量 $x_i$ を入力し、LightGBMの組込みobjectiveを使う。

```python
LGBMRanker(objective="lambdarank")
```

レースごとに馬の行を連続させ、`group`にはその並び順で各レースの行数を渡す。`sum(group)`は特徴量・ラベルの行数と等しくする。レースIDの配列を`group`として渡す仕様ではない。評価データにも対応するレース単位のgroupを用意する。[LGBMRankerの公式API](https://lightgbm.readthedocs.io/en/stable/pythonapi/lightgbm.LGBMRanker.html)

教師ラベルは次の整数とする。ラベルとNDCGのgainは別であり、MVPではLightGBMの既定gain $G(y)=2^y-1$ を用いる。[LambdaRankとlabel_gainの公式仕様](https://lightgbm.readthedocs.io/en/stable/Parameters.html#label_gain)

| 確定着順 | 教師ラベル $y_i$ | gain $G(y_i)$ |
| --- | --- | --- |
| 1着 | 3 | 7 |
| 2着 | 2 | 3 |
| 3着 | 1 | 1 |
| 4着以下 | 0 | 0 |

主指標はレースごとのNDCG@3の平均とする。補助指標はTop1精度（予測首位が実際の勝者だったレースの割合）とTop3一致割合（予測上位3頭と実際の上位3頭の共通頭数を3で割り、レースごとに平均）とする。Top3一致割合は順序を評価しないため、NDCG@3と区別する。同着等で上位3頭が一意に定まらない場合のラベル・指標、取消・除外、3頭未満、予測スコア同値の扱いは、実装前に別途決める。未決定の例外を自動的に除外する規則は追加しない。

出力はレース内の順位付けスコア $s_i$ と、その降順で並べた馬である。

$$
x_i \longrightarrow \mathrm{LightGBM} \longrightarrow s_i
$$

$s_i$ は勝率や馬単・3連単の確率ではない。スコアにsoftmaxを後付けしても、PLの尤度で学習したモデルにはならない。MVPの成果はランキング性能であり、確率、期待値、購入案は出さない。

### 拡張: top-3 Plackett–Luce custom objective

ランキング性能を検証した後、着順確率とオッズを比較するための拡張として、top-3 Plackett–Luce（PL）の負の対数尤度をLightGBMのcustom objectiveで最適化する方針とする。以下は、同着、取消・除外、返還のない通常の的中条件に対する確率式であり、例外への適用方法を確定するものではない。

同一レースの対象馬集合を $A_r$、実際の第 $k$ 着の馬を $\pi_{r,k}$ とし、各馬の潜在的な強さを次のように定義する。

$$
s_i=f(x_i), \qquad \lambda_i=e^{s_i}
$$

1〜3着が相異なる馬 $i,j,k$ である確率は、全馬から1着を選び、その馬を除いて2着、さらに選ばれた2頭を除いて3着を選ぶ確率の積となる。

$$
P(i\to j\to k)
=
\frac{\lambda_i}{\sum_{l\in A_r}\lambda_l}
\frac{\lambda_j}{\sum_{l\in A_r\setminus\{i\}}\lambda_l}
\frac{\lambda_k}{\sum_{l\in A_r\setminus\{i,j\}}\lambda_l}
$$

第 $k$ 段階の残りの馬集合を
$S_{r,k}=A_r\setminus\{\pi_{r,1},\ldots,\pi_{r,k-1}\}$ とする。4着以下の馬も、選ばれていない限り分母に含む。レースごとの損失と学習対象の損失は次のとおりである。

$$
L_{\mathrm{PL},r}
=
-\sum_{k=1}^{3}
\log\frac{e^{s_{\pi_{r,k}}}}{\sum_{j\in S_{r,k}}e^{s_j}},
\qquad
L_{\mathrm{PL}}=\sum_r L_{\mathrm{PL},r}
$$

この損失の勾配と各行のHessian対角項をレース単位で計算し、LightGBMが要求する`grad, hess`として返すcallableを実装する。PLを指定する組込みobjective文字列を想定しない。`group`を受け取るcustom objectiveのAPIに従い、レース内で結合した損失の微分、対角項を用いた学習、`logsumexp`による数値安定性を実装前に検証する。[custom objectiveの公式API](https://lightgbm.readthedocs.io/en/stable/pythonapi/lightgbm.LGBMRanker.html)

この拡張では、次の一貫した確率モデルから単勝、馬単、3連単の確率を計算する。単勝は上式の第1項、馬単は第2項までの積、3連単は3項すべての積である。

$$
x_i \longrightarrow s_i \longrightarrow \lambda_i
\longrightarrow P(\text{着順})
$$

確率から、同じ判断時点の対象買い目のオッズを用いて、購入額に対する期待純収益率 $EV=P\times Odds-1$ を評価する。ただし、この式も通常的中時の払戻倍率を用い、手数料を含まない。同着、取消・除外、返還、特払いとオッズ変動を伴う購入判断への適用は別途仕様化する。確率を生成できることだけで、実測の校正、市場超過、利益が確認されたとは扱わない。

## Rationale

LightGBMの標準LambdaRankを使えば、独自の確率損失と微分を実装する前に、特徴量と上位馬のランキング性能を検証できる。出力の意味を順位に限定することで、順位付け用のスコアを確率として購入判断に流用する誤りを避けられる。

top-3 PLを直接学習する拡張は、単勝・馬単・3連単を同じ潜在的な強さから計算できる。ただし、2・3着にも同じ強さを使うという構造仮定が実際の競馬に合うか、着順段階別・券種別に検証する必要がある。ランキングの改善は確率校正の改善や収益を保証しない。

## Validation / Follow-up

1. オッズ、発売対象馬、特徴量、取消等の発表時刻と受信時刻、着順、払戻、購入可能性を監査する。発走5分前の提示に間に合う入力固定時刻は処理時間の実測から定める。履歴を再現できない過去期間を最終オッズで代用せず、必要な時刻付き保存と観測運用で評価データを作る。
2. レースを分割単位とする時間順の拡大型Walk-forwardを継承する。同じレースの馬を学習と評価へ分けず、各外側期間より過去の内側期間だけで特徴量、ハイパーパラメータ、校正、購入方策を決める。最終の未来期間はモデル選択に使わない。評価対象はJRA平地重賞とし、学習対象の範囲は別途比較する。
3. MVPはNDCG@3、Top1精度、Top3一致割合を報告する。同時点の有限で正の単勝オッズと発売対象馬の完全なスナップショットを確認できるレースでは、単勝オッズ昇順の市場ランキングと、同じ対象馬・レース・入力固定時刻で比較する。NDCG@3の平均差とレース単位の対応ありbootstrapによる95%信頼区間を併記する。オッズ履歴がない期間のランキング評価は同時点市場比較と区別する。
4. PL実装時は、小さなレースで損失・勾配・Hessian対角項を有限差分と照合し、レース境界、極端なスコア、確率の総和、単勝・馬単・3連単の整合性を検証する。MVPと同じ時点・レースでランキング性能を比較し、加えて着順段階別・券種別の確率校正を確認する。
5. PLの単勝確率は、同時点の市場基準 $q_i=(1/O_i)/\sum_{j\in A_r}(1/O_j)$ と、勝者のレース単位Log Loss、全馬の多クラスBrier Score、オッズ帯・予測確率帯・購入候補帯の校正で比較する。$q_i$ は真の勝率ではない。Log Lossの市場との差にレース単位の対応ありbootstrapによる95%信頼区間を付け、上限が0未満のときだけ市場超過の証拠とする。信頼区間が0をまたぐ場合は優位性未確認と報告する。単勝での改善だけで連勝式の確率を採用せず、券種別の検証を行う。
6. 同着、入力固定後の発売対象馬変更、取消・除外、返還等の学習・予測評価への扱いは、各段階の実装前に決める。入力固定後の情報で過去の予測対象や分母を書き換えず、評価対象と件数・理由を明示する。購入方策の評価では確定した精算に従う。

### 継承する購入方策・予算・精算規則

購入方策は予測モデルと別に評価する。方策、期待利益の安全幅、損失リスク制限、100円単位の金額、見送り条件を内側の期間で固定する。購入案は発走5分前までに提示し、利用者が購入する。七券種は調査・比較対象に残し、購入案への追加は各券種の確率・オッズ・払戻の検証後に決める。

過去検証では仮想購入額、運用では記録した実購入額を用い、暦年100,000円・1レース5,000円の額面購入額上限を判定する。払戻で購入可能枠は増やさず、返還も購入済み額面から差し引かない。実購入額が把握できず上限を確認できない場合は購入を提案しない。

購入判断にはその時点のオッズを使い、事後の確定払戻は精算に使う。暦年の券面回収率は`確定払戻・返還に基づく受取額（特払いを含む）÷額面購入額`、純利益は`同受取額−額面購入額−手数料`とする。特払いを通常払戻と重複計上しない。購入額0円の年の回収率は定義せず、手数料が未確認の期間は純利益を確定値として報告しない。

購入レース数、的中率、最大ドローダウン、最大連敗、累積純損益の推移と、レース単位bootstrapによる回収率の不確実性を暦年ごとに報告する。累積純損益は年初0円から購入レース順に純利益を積み上げ、最大ドローダウンはその累積値の過去最高値からの最大下落額（円）とする。仮想購入と実購入の実績を分け、年間回収率100%以上は目標として扱う。

## Consequences

### Positive

組込みのランキングobjectiveから始め、上位馬の並び順に関する性能を先に測定できる。PL拡張では、同じモデルから通常的中条件の単勝・馬単・3連単確率を計算できる。

### Negative

MVPでは確率も購入案も得られず、確率推定に関するREQ-03の達成を判断できない。PL拡張には損失と微分の実装、数値検証、確率校正、券種別の検証が必要となる。重賞の少ない評価標本や高額的中への依存は、不確実性を大きくする。

### Neutral / Follow-on effects

この決定はモデルの設計方針を変更する。モデルの実装、LightGBM依存の追加、永続モデル形式、購入画面は今回の変更に含めない。実装時は既存のParquet読み込み境界を使い、モデルの依存関係を`pyproject.toml`と`uv.lock`へ追加して検証する。

## Alternatives Considered

- **ADR-004の市場補正型単勝モデルをMVPとして継続:** 単勝確率を直接学習できるが、今回の「まず上位馬を並べる」という段階構成に合わせて交代する。元の判断理由はADR-004に残す。
- **最初からtop-3 PLを実装:** 着順確率を直接学べるが、特徴量とランキング性能の検証より先に独自objectiveの実装・検証が必要になるため、拡張段階とする。
- **LambdaRankスコアを後処理だけで確率化:** PL損失による学習と同一ではなく、確率の実測校正も保証されないため、PL拡張の代用にはしない。

## Risks

| Risk | Impact | Mitigation |
| --- | --- | --- |
| 発走前に使えなかった情報の混入 | 順位・確率・利益を過大評価する | 発表・受信時刻を監査し、時間順検証を行う |
| スコアを確率として利用 | 根拠のないEVや購入案になる | MVP出力を順位に限定し、PL拡張で確率を学習・検証する |
| PLの同一強さによる逐次選択が競馬に合わない | 2・3着や連勝式確率が偏る | 着順段階別・券種別の校正を確認し、必要な補正は別途決定する |
| 同着・取消等の規則が未確定 | ラベル・評価・精算が食い違う | 実装前に扱いを定め、件数・理由と確定精算を記録する |

## Security / Privacy Impact

認証・秘密情報・外部通信の境界は変更しない。データ取得、加工後データの読み込み、ローカル保存の既存規則を維持する。

## Migration / Rollback

未実装のモデル方針を変更するため、学習済みモデルやデータの移行はない。ADR-004をSupersededとして歴史的決定を保存し、仕様書、要件定義、ARCHITECTURE.mdの参照をこのADRへ更新する。方針を再変更する場合も、理由を新しいADRに記録する。

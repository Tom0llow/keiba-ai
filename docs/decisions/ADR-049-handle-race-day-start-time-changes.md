# ADR-049: 当日の発走時刻変更を速報で確認し、取得と保留を分けて扱う

- Status: Proposed
- Date: 2026-11-24
- Decision Owners: Repository maintainers
- Related Issues/PRs: Refs #31・#57
- Supersedes: N/A
- Superseded by: N/A

---

## Context

race-day-oddsは起動時に前日夜の`latest`の出馬表から`HassoTime`を1回読み、30・10・5・2分前の
オッズ取得と、5分前の予測用取得を計画する。起動後に予定は変わらない。ADR-032は発走時刻の変更に
追従しないとし、ADR-037、ADR-039、ADR-041は、当日の特徴量、予測、発売締切について発走時刻変更の
扱いを#31へ送っている。ADR-046は#31に触れていないが、購入案の要求時刻を出馬表の発走時刻から決めるため、
変更前の出馬表の時刻に依存する関連の決定である。

`docs/experiments/race-day-start-time-change.md`の集計では、最終RAの`HassoTime`と
`HassoTimeBefore`が異なるレースは2014年以降の毎年存在し、2020年以降は+1分の繰下げが約87%を占める。発走時刻変更の
速報は、日付のキーで要求する`0B14`の`RT_TC_INFO`に変更前後の時・分と`HappyoTime`として届いた。
観測した+1分の3件は、開催日の08:20 JSTに発表されていた。発表は前日夜より後なので、前日夜の`latest`の
出馬表には載っていないと推定する（その日の`NL_RA_RACE`の途中の状態は観測していない）。

一方、最終RAの差分で繰上げが0件だったことは、当日の途中状態に繰上げがないことを保証しない。繰上げでは、
前日夜の予定に固定したfreezeが新しい発売締切の後になりうる。変更後の発走を基準にすべてを動かすと、
繰下げ時の予測と購入案の提示を遅らせる。また、当日の特徴量の常駐CLIは、出馬表の発走時刻と予測用取得の
`scheduled_start_at`が一致することを前提にしている（ADR-037）。なお、学習用datamartは確定した
`HassoTime`（変更があったレースでは変更後の時刻）の5分前をfreezeにしている（ADR-034）。

このADRは、実装の前に方針を決めるProposedの記録である。確認の時点や記録の形式などの仕組みの細部は、
後続の実装のIssueで決め、このADRをAcceptedにするときに書き足す（「実装で決める事項」）。現時点では
コード、保存形式、既存ADRの本文を変えない。

## Decision

1. **変更の情報源と確認。** race-day-oddsは、対象日の日付のキーで`0B14`を要求し、`RT_TC_INFO`を読む
   （以下、TC確認）。TC確認は、起動・再開のときと、各時点（同時刻の`kind="prediction"`と
   `kind="capture"`をまとめたもの）の前に行う。予測用取得の時点も含む。TC確認のために取得を予定時刻より
   後へ遅らせない。時点の前にTC確認を終えられないときは、その時点の取得を直前に分かっている予定で行う。
2. **変更後の発走時刻と再計画。** TC行は、その日のTC確認で得た行を蓄積して扱う。後の成功した応答に
   以前の行が無くても、その行は消えたものとせず、新しい情報がないものとする。レースの変更後の発走時刻は、
   その日に蓄積したそのレースのTC行のうち、最も新しい発表（`HappyoTime`）の変更後の時刻とする。変更後の発走時刻が起動時に読んだ出馬表の
   `HassoTime`より後なら繰下げ、前なら繰上げ、同じなら変更なし（いったん変わった後に元へ戻った場合を含む）
   とする。まだ完了していない（取得記録に終端の状態`archived`・`no_data`・`failed`・`skipped_late`・
   `interrupted`のいずれもない）`kind="capture"`の30・10・5・2分前の取得は、方向に関係なく、その時点の
   変更後の発走時刻（変更なしなら出馬表の`HassoTime`）で計画し直す。`kind="prediction"`は、繰下げでも
   繰上げでも出馬表の予定のままとする。遅延の判定は既存どおり各取得の予定時刻（再計画した取得では
   再計画後の予定時刻）と`late_tolerance_seconds`を基準にする。
3. **確認の結果。** `0B14`が該当データなしの`-1`、または`-1`以外の失敗のときは、新しい情報がないものとして、
   直前に分かっている予定で続ける（出馬表の予定へは戻さない）。失敗はstderrに出す。`JVOpen`または
   `JVRTOpen`の`-211`・`-303`は、ADR-032 Amendment 3の既存規則どおり、記録後に残りの取得を実行せず終了する。
   TC確認の結果と、どのTC行（少なくともレースごとに採った変更後の時刻と`HappyoTime`）で計画したかを
   永続して残す。その記録先と形式は実装で決める。
4. **freeze、予測、購入案の時刻。** 当日の特徴量のfreeze、`kind="prediction"`の取得、PL予測の
   `after_sales_close`、購入案の要求時刻は、前日夜の`latest`の出馬表にあった変更前の予定のままとする。
   最終RAの差分では繰下げだけが観測されているため、繰下げなら予測は変更後の発売締切より前に出る。
   このため、繰下げのあったレースでは、当日のfreezeは学習用datamartのfreeze（確定＝変更後の`HassoTime`の
   5分前）より変更幅だけ早くなる（多くは1分、観測の最大は110分）。学習用datamart、評価、バックテストの
   確定した`HassoTime`を使う規則は、このADRの対象外とする。
5. **繰上げの保留。** その日に蓄積したそのレースのTC行のどれかの変更後の時刻が出馬表の`HassoTime`より
   前のとき、繰上げを検出したとする（同じTC確認で元の時刻へ戻る行も得て、変更後の発走時刻が繰上げに
   ならない場合を含む）。このとき、race-day-oddsは決定2のとおり未完了の`kind="capture"`だけを
   計画し直し、stderrへ通知する。さらに、そのレースについて、当日の特徴量、PL予測、購入案の3つの常駐CLIが
   読める永続の印を残す。印のあるレースでは、特徴量の常駐CLIはそのレースの特徴量を公開せず、PL予測の
   常駐CLIは予測を公開せず、購入案の常駐CLIは購入案を公開しない。3つとも、保留の理由（繰上げ）を出力する。
   印は、その後の発表で出馬表の時刻へ戻っても、その日の間は消さない（3つの常駐CLIは保留のままとする）。
   予測用取得の前のTC確認で繰上げを検出した場合は、その予測用取得より前に印を残す。予測用取得の後に
   検出した繰上げでは、既に公開した特徴量、予測、購入案をこのADRでは取り消さない。印とstderrに残し、
   人が当日の発表で判断する。
6. **取得記録と再開。** `ARCHIVE_CAPTURE_LOG`の`scheduled_start_at`は、起動時の出馬表にある変更前の
   予定として残す。各行を計画したときの発走時刻が出馬表の`HassoTime`と違うときは、その時刻を新しい列
   `effective_start_at`に残し、同じときは`NULL`とする。既存の行は`NULL`とする。完了済みの判定は現行の
   `race_id`・`offset`・`kind`を保ち、変更後の時刻を理由に同じoffsetを取り直さない。取得記録の行を書く前に
   失敗した取得（`failed/capture_not_recorded`）は、その実行の中では使ったものとして計画し直さず、再開のときは
   今の再開の規則（取得記録の行がない取得は行う）に従う。

このADRのレビューで確かめた制約である。

| 事項 | 要件 |
| --- | --- |
| TC確認の時点と上限時間 | 取得は1回に最大`execution_timeout_seconds`（120秒）かかり、時点の間隔は最短で約1〜2分（開催日により最長は10分を超える）、`late_tolerance_seconds`は60秒である。TC確認には取得とは別の短い上限時間を設け、取得を遅らせない。前の時点の取得が長引いて確認の時間が残らないときの省略と、その記録を決める。1回の確認で近い複数の時点を兼ねてよい。 |
| TC確認の結果の記録先 | `ARCHIVE_CAPTURE_LOG`はレース・offset・DataSpecの行で、再開の判定にも使うため、日単位の確認をそのまま入れない。新しい表をraw DBに置くなら、全列をTEXTにする（完全snapshotはraw DBの全表を書き出し、`src/data/preprocessor/sqlite_to_arrow.py`はTEXT・DATETIME以外の宣言型と文字列以外の値を拒否する）。 |

| `0B14`が作る他の表 | `0B14`は`RT_TC_INFO`のほかに`RT_AV_INFO`・`RT_WE_WEATHER`・`RT_JC_INFO`（観測なしの`RT_CC_INFO`もありうる）をraw DBに作り、完全snapshotに書き出される。その扱いと文書を決める。 |

| `effective_start_at`の移行と切り戻し | 既存DBへの列の追加を1回だけ行う。古いコードは`ARCHIVE_CAPTURE_LOG`の列の完全一致を求めるため、切り戻しは当日の取得（発走の後には取り直せない）を失わない方法で行う（例: 行を残して列だけを削る）。移行前のDBの複製を戻すのは、移行の後に取得を書いていない場合に限る。 |

## Rationale

`0B14`の`RT_TC_INFO`は、当日08:20に発表された変更（前日夜の出馬表には載っていないと推定される）を、
対象レースと変更前後の時刻に結び付けて返した。各時点の前に確認すれば、その前までに発表された変更を未完了のオッズ取得へ反映できる。確認のために
取得を遅らせなければ、確認の失敗や遅れが取得そのものを損なわない。

繰下げでは、前日夜の予定を基準とする5分前のfreezeと予測用取得は、変更後の発売締切より早い。これを
変更後の発走時刻へ動かさなければ、当日の特徴量の常駐CLIの時刻契約（ADR-037）を変えず、締切に遅れる
リスクも増やさない。その代わり、学習用datamartのfreeze（確定＝変更後の`HassoTime`の5分前）とは変更幅だけ
ずれる。変更の約87%は+1分であり、このずれは小さいことが多い。繰上げは最終RAの差分では観測していないが、
起きた場合に古いfreezeを使うことは安全でないため、特徴量、予測、購入案を保留する。印をその日の間は
消さないのは、特徴量の常駐CLIの保留を取り消す仕組みがなく、保留したままにする方が単純で安全だからである。

`scheduled_start_at`と`effective_start_at`を分ければ、起動時に予定した時刻と、各取得を計画した時刻を
監査できる。既存の完了判定を変えないため、再開時に同じoffsetの取得を重複させない。

仕組みの細部は、取得の時間配分、raw DBとsnapshotの型、作り直されうる受け皿の表、切り戻しの損失など、
実装の設計と一緒に確かめるべき制約に強く依存する。そのため方針と分けて実装のIssueで決める。

## Consequences

### Positive

- 発走の繰下げが当日に発表されても、時点の前までの発表なら、まだ行っていないオッズ取得を変更後の時刻へ
  合わせられる。
- 変更前後の発走時刻とTC確認の結果を残し、取得時点を事後に説明できる。
- 予測用取得の前に分かった繰上げでは、別プロセスにも届く永続の印によって、特徴量、予測、購入案を保留できる。

### Negative

- 各時点の前に`0B14`を要求するため、race-day-oddsの実行回数と、TC確認の結果を記録する経路が増える。
- `ARCHIVE_CAPTURE_LOG`に列を追加する移行と、永続の保留状態の設計が必要になる。
- 繰上げを検出したレースでは、特徴量、予測、購入案を出さない。
- 時点の直前に発表された変更や、前の時点の取得が長引いて確認できなかった変更は、その時点の取得には
  反映されず、次の時点から反映される。そのレースの最後の時点（2分前）の後に分かった変更は、そのレースの
  取得には反映されない。完了したoffsetは変更前の基準のまま残る。
- 予測用取得の後に分かった繰上げでは、公開済みの出力が残る。
- 繰下げのあったレースでは、当日のfreezeが学習用datamartのfreezeより変更幅だけ早い（多くは1分、観測の最大は
  110分）。大きな繰下げでは、特徴量、予測、購入案が実際の発走より古い時点の情報になる。
- 購入案の要求時刻（ADR-046）を変更前の予定で決めるため、繰下げのあった先の重賞では、変更前の発売締切の後で
  変更後の発売締切より前に行った購入が、後の重賞の購入案の上限に含まれないことがある（重賞の変更は2016年以降で
  5件とまれである）。
- ADR-047の評価は、確定の`HassoTime`−300秒をfreezeとしてワイド・馬単の取得を選ぶ。時点の前に変更が分かり
  取得を変更後の時刻で計画し直せば、繰下げのあったレースでも5分前の取得を選べる。計画し直さないと、約+9分を
  超える繰下げでは5分前の取得を選べず、約+12分を超える繰下げでは選べる取得がない（発表は取得の約1分前）。一方、同じレースの当日の特徴量とPL確率は変更前の予定のfreezeで作るため、評価の中で
  特徴量とオッズの時点が繰下げの幅だけずれる。扱いは後続の実装（Implementation Notesの段階4）で決める。

### Neutral / Follow-on effects

- 繰下げ時もfreeze、予測用取得、`after_sales_close`、購入案の要求時刻は変更前の予定のままである。
- `0B14`の保持期間、当日の速報の到達時点、当日の途中状態は、必要なら後続の実装の前に追加で観測する（Follow-up）。`latest`の速報設定が固定日のままである問題は、
  この決定の実装範囲外である。
- このADRがProposedの間は、保存形式やCLIの実装は変わらない。

## Alternatives Considered

### Option A: 変更後の発走時刻へfreeze、予測、購入案も移す

Summary:

`RT_TC_INFO`で繰下げを検出したら、すべての当日処理を変更後の発走時刻へ移す。

Advantages:

- 当日のすべての処理が同じ変更後の時刻を基準にする。
- 学習用datamartのfreeze（確定＝変更後の`HassoTime`の5分前）と一致する。

Disadvantages:

- 繰下げでも予測と購入案の提示を遅らせる。変更の発表がfreezeの直前だと、計算の時間が足りず発売締切に
  間に合わない可能性が増える。
- 当日の特徴量の常駐CLIの時刻契約（出馬表の発走時刻と予測用取得の照合、ADR-037）を変える必要があり、
  3つの常駐CLIがTC確認の結果を読む実装が要る。

Reason not selected:

最終RAの差分で観測された変更は繰下げだけであり、変更前の予定の5分前でも変更後の発売締切より前に予測できる。
学習とのずれは変更の約87%で1分と小さく、当日の常駐CLIの契約を変える実装の大きさに見合わないため
（2026-11-24の中間のゲートの人の決定）。

### Option B: 起動時だけ`0B14`を確認する

Summary:

race-day-oddsの起動時にだけ`0B14`を要求し、その後の予定は変えない。

Advantages:

- 要求回数と実装が少ない。

Disadvantages:

- 起動後に発表された変更を、まだ実行していない取得へ反映できない。

Reason not selected:

観測した変更は開催日の08:20に発表され、その前に起動した場合は、起動時だけの確認ではその日の変更を
すべて取りこぼすため。各時点の前の確認なら、取りこぼすのは時点の直前の発表だけになる。

### Option C: 繰上げでも前日夜の予定で処理を続ける

Summary:

繰上げを検出しても、予測と購入案を含めて予定を変えずに処理する。

Advantages:

- 保留状態と下流CLIの連携を追加しない。

Disadvantages:

- freezeが新しい発売締切の後になり、購入判断に使えない予測を出すおそれがある。

Reason not selected:

繰上げは最終RAの差分で未観測でも、起きた場合の時刻契約違反を避ける必要があるため。

3. 購入案の常駐CLIが同じ印を読み、対象レースを保留するようにする。

## Risks

| Risk | Impact | Mitigation |
| --- | --- | --- |
| `0B14`が一時的に失敗する | 変更を反映できない取得がある。繰上げの検出が予測用取得の後になると、特徴量・予測・購入案を保留できない | 新しい情報がないものとして直前の予定で続け、失敗を残す。`-211`・`-303`は既存規則どおり停止する。TC確認の失敗が続くときは、人が当日の発表で発走時刻を確かめる。 |
| TC確認が遅い・止まる、または前の時点の取得が長引く | 確認が時点に間に合わない。繰上げの検出が遅れると、上と同じく保留できないことがある | 取得を遅らせず、直前の予定で取得する。確認の上限時間と省略の記録は実装で決める。 |
| 速報の保持期間を越えてTCを確認する | 過去日の変更を再確認できない | 当日の各時点の前に確認し、結果とTC行を永続する。保持期間は、必要なら後続の実装の前に追加で観測する（今回の観測では3日以上9日未満）。 |
| 繰上げの印が下流CLIへ届かない | 発売締切後のfreezeで予測または購入案を出す | stderrだけに依存せず、3つの常駐CLIが読む永続の印を実装する。 |
| 予測用取得の後に繰上げが分かる | 公開済みの予測や購入案が残る | 印とstderrに残し、人が当日の発表で判断する。 |
| 繰下げで当日のfreezeが学習より早くなる | 大きな繰下げでは古い時点の情報で予測・購入案を出す | 変更の約87%は+1分。大きな繰下げのレースは、人が当日の発表を見て購入を判断する。 |
| 繰下げのあった先の重賞の購入が台帳の確認に間に合わない | 後の重賞の購入案の上限が残りの予算を多く見積もる | 先の重賞の発走時刻が変わったら、人は変更後の発売締切の後に台帳を確認する。 |
| `ARCHIVE_CAPTURE_LOG`の列追加後に古いコードへ戻す | 旧コードの列完全一致検査がDBを拒否する。DBの複製を戻すと当日の取得を失う | 当日の取得を失わない切り戻しの方法を実装で決める。 |

## Security / Privacy Impact

セキュリティやプライバシーへの重大な影響はない。既存のローカル取得、SQLite記録、当日のCLI間の状態だけを
扱い、認証情報、個人データ、外部への送信を新たに扱わない。

## Operational Impact

当日のrace-day-oddsは、起動、再開、各時点の前に`0B14`を確認する。確認の失敗と繰上げはstderrに出て、
TC確認の結果は永続する。繰上げの永続の印があるレースは、当日の特徴量、PL予測、購入案を保留する。

## Migration / Rollback

### Migration

実装時に、既存の`ARCHIVE_CAPTURE_LOG`へ`effective_start_at`を1回だけ追加する。既存行は`NULL`とし、
`scheduled_start_at`の意味を変更しない。TC確認の記録、TC行の永続、繰上げの印の形式は、実装で決める。

### Rollback

当日の取得は発走の後には取り直せないため、切り戻しはそれを失わない方法で行う。具体的な手順は実装で決め、
このADRをAcceptedにするときに書き足す（「実装で決める事項」）。

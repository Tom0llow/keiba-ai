# 計算済みの列の追加の試行

## 目的と範囲

[ADR-051](../decisions/ADR-051-add-calculated-card-and-history-columns-and-decide-at-the-yearly-rebuild.md)は、閉じた数値列に
計算済みの8列（枠番・頭数・馬齢・過去の3着内率・前走〜4走前の符号付き着差）を加え、採否を2027年向けの作り直しで決める。
この記録は、採否の前に行った試行の結果である。運用と同じ固定snapshotからdatamartを構築し、test 2016〜2025年の評価と
最終学習を行って、変更前の結果を再現できるか、加えた列の欠損と欠損の枝の照合、指標とablation、Issue #83の区分ごとの
残差を確かめた。

2016〜2025年は、加える列の仮説を選ぶのに使った期間である。そのため、この試行の結果は採否の根拠にしない。
採否は、test年2026を含む作り直しの評価で決める。

## 実行

worktree（この変更のブランチ）から、運用のcheckoutの`data/processed`と`output/`を絶対パスで指定して実行した。

```powershell
uv run python src/main.py datamart build-reference --config-name measure --override processed_root=<data/processed> --override snapshot_id=098ce3f4b5d7480282269218d80cef05 --override target_start=2006-01-01 --override target_end=2025-12-31 --output <output/reference-datamart-2006-2025-added-columns>
uv run python src/main.py model evaluate-pl --config-name measure --override processed_root=<data/processed> --override datamart_path=<上のdatamart> --override datamart_manifest_sha256=<manifestのSHA-256> --output <output/pl-evaluation-2016-2025-added-columns>
uv run python src/main.py model evaluate-pl --config-name measure （上と同じ上書き） --override lightgbm.seed=1 --override "variants=[{name:all_columns,excluded_columns:[]},{name:without_added_columns,excluded_columns:[<加えた8列>]}]" --output <output/pl-evaluation-2016-2025-added-columns-seed1>
uv run python src/main.py model train-pl --config-name final --override datamart_path=<上のdatamart> --override datamart_manifest_sha256=<manifestのSHA-256> --override variant.name=all_columns --override "variant.excluded_columns=[]" --output <output/pl-final-model-2006-2025-added-columns>
uv run python src/main.py model backtest-betting --config-name measure --override processed_root=<data/processed> --override pl_evaluation_path=<7 variantの評価> --override pl_predictions_sha256=<predictions.parquetのSHA-256> --override pl_report_sha256=<report.jsonのSHA-256> --output <output/ev-betting-backtest-2016-2025-added-columns>
uv run python src/main.py model fit-betting-estimator --backtest <上のバックテスト> --backtest-report-sha256 <バックテストのreport.jsonのSHA-256> --pl-evaluation <7 variantの評価> --processed-root <data/processed> --output <output/ev-betting-estimator-2026-added-columns>
```

バックテストは`pl_variant`・`test_years`（2016〜2025年）とも`configs/betting_backtest/measure.yaml`の既定のままである。

## 条件

- 固定snapshot: `098ce3f4b5d7480282269218d80cef05`（運用のdatamartと同じ）。datamartの設定は運用のdatamartのmanifestの
  `preparation_config`と同じ（対象2006-01-01〜2025-12-31）。
- 比べる相手: 運用のdatamart`output/reference-datamart-2006-2025`（manifest SHA-256 `dc37514732fdb653ce9ed3a6e836a0f6f120a5613a905c5574d43cdc0f4b51b9`）と、運用の評価
  `output/pl-evaluation-2016-2025-graded-final3`。
- 評価の設定は`configs/pl_evaluation/measure.yaml`の7 variant（LightGBMのseed 0）。揺らぎの目安として、seed 1で
  `all_columns`と`without_added_columns`だけをもう1回評価した。
- 機械: 開発用のWindows 11の1台（論理16コア、メモリ32 GB）。LightGBM 4.7.0、`num_threads` 8、`deterministic`。
- 所要時間・CPU時間・ピークcommitは、CLIをWindowsのジョブに入れて子孫のプロセスまで測る計測用のスクリプト（コミットしない）で
  測った。指標の再計算・bootstrap・区分の残差も、計測用のスクリプト（コミットしない）で`predictions.parquet`から求めた。
- 日付: 2026-11-26〜27。

## 運用のdatamartとの一致

運用のdatamartと、年ごと（2006〜2025年）に直接比べた。

- 計算契約の`selected_columns`は、先頭36列が運用のdatamartと同じ名前・同じ順で、その後ろに加えた8列が続く。
- `held_races.json`のSHA-256は一致した（保留21,150件）。
- 全20年で行数が一致し、行を(race_id, horse_id)で並べたとき、`race_id`・`horse_id`・`scheduled_start_at`・`freeze_at`・
  先頭36列・全`*__available_at`・`finish_position`が完全に一致した（計835,398行・59,115レース）。
- `races.parquet`はファイルのSHA-256が全年で異なるが、表の中身は全年で一致した。違いは、ファイルのメタデータに入る
  計算契約のSHA-256だけである。

## 運用の評価との一致

`without_added_columns`（変更前の36列と同じ列・同じ順）を、運用の評価の`all_columns`と比べた。

- `predictions.parquet`の412,931行で、`race_id`・`horse_id`・着順・score・温度・`p_win`・`p_top2`・`p_top3`が完全に一致した
  （差の最大0）。
- 10 foldのすべてで、`best_iteration`と温度が一致した。

列を加えても、元の36列の計算と学習は変わらない。

## 運用のバックテストと推定器との一致

7 variantの評価結果に、既定の`pl_variant`（`without_added_columns`）でバックテストと推定器の作成を行い、運用の結果（バックテストの

## seedを変えた揺らぎ

同じ列でseedだけを変えた差（seed 1−seed 0）は、`all_columns`の単勝で+0.000432（95%区間[−0.000273, 0.001157]）、
`without_added_columns`の単勝で+0.000105（[−0.000636, 0.000897]）だった。連系でも差は最大+0.0012程度である。
加えた列による差（単勝−0.00088、連系−0.001〜−0.0018）は、seedによる揺らぎと同じ大きさである。seed 0とseed 1のどちらでも、
差の向きは全指標で改善側だった。

## Issue #83の区分ごとの残差

test 2016〜2025年の校正後の確率で、区分ごとに「実際の勝ち数÷勝率の和」と「実際の3着以内の数÷3着以内の確率の和」、
z=(実際−Σp)/√Σp(1−p)を求めた。1より小さい比は、モデルがその区分を過大に評価していることを示す。

## 制約

- 2016〜2025年は、加える列の仮説を選ぶのに使った期間であり、この結果は採否の根拠にならない。
- 加えた列による差は、seedによる揺らぎと同じ大きさである。2027年向けの作り直しでも、1回の評価の差だけで判断しにくい。
- 前走（lag1）と3着内率は、datamartの過去成績の定義に従う。数えるのは、中央10場で`history_start`（2005-01-01）以後の
  通常結果のレース（`make_features/reference_raw.py`の`normal_result`。出走馬の全員が`IJyoCD`=0・`DochakuKubun`=0で、着順が
  1〜頭数でそろい、結果の行の`headMakeDate`が結果の利用開始日より前であることなど）のうち、freezeの時点で結果が使えるもの（`result_delay_days`=7。
  レース日の8日後の0時（JST）から）だけである。取消・除外・降着・同着のあるレースは数えず、7日前の出走（連闘）も前走にならない。
  2005年より前にしか出走のない馬は、過去成績がない馬として欠損になる。
- ablationの差は、共線性のため各群だけの寄与ではない。
- 評価のtestは学習と同じdatamartから作るため、freezeの時点のO1に出ていない取消・除外のあるレース（通常結果でないので除かれる）を含まない。当日はそのようなレースも出走表の頭数で予測するので、頭数の列の学習と当日のずれの影響は、この指標に現れない（[年次の再学習手順](../retraining-operation.md)で、採否の前に件数を数える）。
- 区分の残差は、区分を事前に選んだうえでの記述であり、多重比較の補正はしていない。
- datamartの構築のCPU時間とピークcommitは測れなかった（構築のピークcommitは、これまでの実測で約8 GB）。44列での値は、
  2027年向けの作り直しで子孫のプロセスまで含めて測る。

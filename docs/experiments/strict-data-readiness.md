## 記録開始後のレースへ絞る場合

新しい観測を保存した後にfreezeを迎えるレースを対象にすれば、利用可能性の証拠を集められる。
過去結果でも、出典・版・観測時刻と必要なソース時刻を保存・検証できれば、その観測完了後にfreezeを迎えるレースの履歴入力として利用できる。過去の発走前へ遡る証拠にはならない。
学習用レースの固定入力、後から観測する結果、さらに未来の評価・予測入力を順に保存する必要がある。
レース数や期間、採用列・業務設定の運用値は、この調査で決定していない。

最小の保存経路は次の設計を候補とする。

1. 取得ロックを、取得開始から固定snapshot公開とreceipt確定まで保持する。
   既存の`retrieve_historical_basic(publisher)`にあるcallback方式を再利用する。
2. 実行前後の実測UTC時計と各観測を保存する。realtimeはRT表の次の置換前に履歴・現在の
   各段階を保存し、挿入0件でも観測の有無を記録する。
3. 固定snapshotのUUID、対象範囲、表別件数・schema・hashを取得runと対応付ける。
   公開成功後に不変receiptを確定し、中断・公開失敗の記録は厳格実験に使わない。
4. 原観測を正規化入力へ対応付け、全21群に必要な出馬表、履歴、調教、血統、条件、
   両オッズanchor、収録完全性を検証する。現在のlatest/realtimeを一度実行するだけで
   これらが全てそろうとは扱わない。
5. 計算後に結果を別入力として結合し、学習結果の利用可能時刻が評価freezeより前であることを
   検査する。MLflowへ固定入力・設定・モデル版・結果を記録する。

受信で示せる利用可能時刻の上限と、元の発表・事象時刻は区別する。
取得できない時刻へ受信日時や作成日を代入しない。保存形式とその時刻の意味は、実装前にADRで定義する。

変更候補は`jra_van_retriever/retriever.py`、`workflows/latest.py`、`workflows/realtime.py`、
取得証跡の型・保存境界、`data/storage/snapshot_builder.py`、`snapshot_publisher.py`、取得CLIである。
旧APIと件数返値を保持し、ロック・公開順、実測時計、RT置換前保存、固定版とhash、公開失敗・中断、
秘密設定を記録しないことを検証する。取得機能とrawからの正規化対応は、今回の計算・モデル接続とは別の未実装部分である。
